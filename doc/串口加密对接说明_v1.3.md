# 门锁 ↔ WiFi 模块 串口加密对接说明

版本：**v1.3**（2026-10-19）
背景：在《串口ACK重传对接说明 v1.1》基础上，明确串口异或加密的密钥体系、密钥交换流程与异常恢复规则。
WiFi 模块侧代码在 `components/obapi/ob_lock/`。

---

## 1. 变更记录

| 版本 | 变更 |
|---|---|
| v1.1 | 命令重编号为 **`0x71 密钥请求` / `0x70 密钥发送`**；`0x00/0x01/0x02` 废弃；`0x02` 回执取消，改用通用 ACK `0xF0` |
| v1.2 | **`0xF1` 回执携带密钥**：门锁收到 `0x71` 时不再单独发 `0x70`，而是直接在 `0xF1` 的 payload 里带密钥，省掉一个来回。<br>⚠️ `0xF1` 是 ACK，**只作为 `0x71` 的应答，不主动发送**；门锁主动补发密钥时仍用 `0x70` |
| **v1.3** | **密钥帧改为 4 字节**：`0x70` / `0xF1` 的 payload 由 1 字节改为 **4 字节随机数**，双方**固定取下标 1（第 2 个字节）作为真正的门锁密钥 `K_L`**；该字节**不得为 `0x00` / `0xFF`**，收到非法值即视为无效密钥并触发重同步。其余 3 字节为填充，不参与运算 |

> **`0x70` 仍然保留** —— 上电时 WiFi 还不知道要请求，门锁必须主动广播一次。

## 2. 密钥定义（3 个，各 1 字节）

| 密钥 | 生成方式 | 用途 |
|---|---|---|
| 出厂密钥 `K_F` | 程序固定 **`0xBA`**（双方固件必须锁定同一值） | 仅用于 `0x70 / 0x71 / 0xF0 / 0xF1` |
| 门锁密钥 `K_L` | 门锁上电随机生成，会话内不变（排除 `0x00` / `0xFF`）；**通过 4 字节密钥帧的下标 1 传递** | 用于其余**所有**帧 |
| 随帧密钥 `R` | 每帧由发送方产生，写入帧头 `random` 字节 | 参与密钥合成；不加密的帧填 `0` |

**实际异或密钥：`key = R ^ K`**（`K` 按命令分派，收发两侧必须一致）

## 3. 命令表

| 命令 | 方向 | payload | 加密密钥 |
|---|---|---|---|
| `0x70` 密钥发送 | 门锁 → WiFi | **4 字节密钥帧**（见 §3.1） | `K_F` |
| `0xF0` 密钥发送回执 | WiFi → 门锁 | 空 | `K_F` |
| `0x71` 密钥请求 | WiFi → 门锁 | 空 | `K_F` |
| **`0xF1` 密钥请求回执** | **门锁 → WiFi** | **4 字节密钥帧**（见 §3.1） | `K_F` |

> `0xF0` / `0xF1` 都是通用 ACK（`cmd | 0x80`），遵守《串口ACK重传对接说明》：最高位=1 的帧不再被应答，也不进重传。

### 3.1 密钥帧格式（4 字节，`0x70` 与 `0xF1` 通用）

| 下标 | 内容 | 说明 |
|---|---|---|
| 0 | 随机字节 | 填充，忽略 |
| **1** | **门锁密钥 `K_L`** | **唯一有效字节**，双方固定取此位置；必须 **≠ `0x00`、≠ `0xFF`** |
| 2 | 随机字节 | 填充，忽略 |
| 3 | 随机字节 | 填充，忽略 |

- **发送方**：4 字节都填随机值，再强制把下标 1 写成 `K_L`（生成时已排除 `0x00/0xFF`）
- **接收方**：**只读下标 1**；若读到 `0x00` 或 `0xFF`，视为无效 → 丢弃并触发重同步（`0x71` / 重发 `0x70`）
- 填充字节**不做"第 2 个非 00"之类的扫描** —— 位置固定，实现简单、无歧义

## 4. 加密规则

1. **只加密 payload**，12 字节帧头（`mark/attr/checksum1/sn/cmd/random/checksum2/length`）始终明文
2. 加密类型标在 `attr` bit4~5：`0` = 不加密（payload 原样）、`1` = 异或
3. **所有帧统一加密（含 payload 为空的 ACK）**：只要密钥已生成就 `enc=1`
   - 空包加密后 payload 仍为空、`checksum2` 仍为 0，**密钥错也能通过校验**，自愈链路不受影响
   - 唯一例外：密钥尚未生成（上电极早期）时退化为 `enc=0`，接收方按明文处理
4. 密钥分派：

| 帧 | `K` |
|---|---|
| `0x70` / `0x71` / `0xF0` / `0xF1` | `K_F` |
| 其余所有 enc=1 的帧 | `K_L` |

5. **校验和语义（判密钥对错的依据）**：
   - `checksum1 = SUM(attr) + SUM(sn ~ payload密文)` —— 密文累加，**任何密钥都能算对**
   - `checksum2 = SUM(payload明文)` —— **只有密钥正确才算得对**
6. **密钥失配判定：`checksum1` 过、`checksum2` 不过 ⇒ 密钥不对**（帧本身没坏），payload 按乱码丢弃

## 5. 交互流程

### 5.1 正常同步（门锁上电）

```
门锁上电 → 生成 K_L（排除 0x00/0xFF）
门锁 → WiFi : 0x70 [4 字节密钥帧]   enc=1, key=R^K_F    (300ms × 2 次 ACK 重传)
WiFi → 门锁 : 0xF0 ACK
WiFi 取 frame[1] 作为 K_L
── 此后双向所有帧：enc=1, key=R^K_L ──
```

### 5.2 密钥失配自愈（门锁重启，WiFi 持旧密钥）

```
门锁(新K_L) → WiFi : 业务帧             enc=1, key=R^K_L(新)
WiFi(旧K_L) : cs1 过、cs2 不过 → 丢帧 → 限频(500ms) 发 0x71
WiFi → 门锁 : 0x71                      enc=1, key=R^K_F
门锁 → WiFi : 0xF1 [4 字节密钥帧]       enc=1, key=R^K_F    ★ 一步到位，不再发 0x70
WiFi 取 frame[1] ── 收敛，恢复正常 ──
```

### 5.3 反向：WiFi 重启（门锁密钥丢失）

```
门锁 → WiFi : 业务帧（加密）
WiFi(无密钥) : 解不开 → 按 5.2 发 0x71 → 门锁回 0xF1 [4 字节密钥帧] → 取 frame[1]
```

### 5.4 门锁主动补发（不依赖对方请求）

门锁收到**加密帧且 cs2 失配**时（说明对端密钥旧了），**主动重发 `0x70` + 4 字节密钥帧**（走 300ms×2 的 ACK 重传，等 `0xF0`），无需等对方发 `0x71`。

> `0xF1` 只作为 `0x71` 的应答，**不主动发送**。

## 6. 收发实现规则（速查）

### 发送侧

| 条件 | 行为 |
|---|---|
| 发 `0x71` | enc=1，`key = R ^ K_F`（不受密钥状态影响） |
| 已持有 `K_L`，发其他帧 | enc=1，`key = R ^ K_L` |
| **发 `0x70` / `0xF1`** | enc=1，`key = R ^ K_F`，payload = **4 字节密钥帧（下标 1 = `K_L`）** |
| 未持有 `K_L`（WiFi 侧） | 每 **500ms** 发一次 `0x71`；业务帧**挂起保序**，拿到密钥后按序补发 |
| 空 payload 的 ACK | **enc=1**（统一加密；payload 为空不影响 `checksum2`=0） |

> WiFi 出货版**没有明文业务帧发送路径**，未拿到密钥时业务帧一律挂起。

### 接收侧

| 帧 | `K` |
|---|---|
| `enc=0` | 不解密（兼容调试/产测） |
| `0x70` / `0x71` / `0xF0` / `0xF1` | `R ^ K_F` |
| 其余 `enc=1` | `R ^ K_L` |

**解完必须校验 `checksum2`**：不过 → 丢帧 + 按 5.2/5.4 处理。

## 7. 门锁侧实现现状（v1.3 已实现）

| 项 | 实现 | 位置 |
|---|---|---|
| `ENCRYPT_EN` | 已打开（`true`） | `common/encrypt/encrypt.h` |
| `K_F = 0xBA` | 宏定义 | 同上 |
| 密钥帧长度/下标 | `LOCK_KEY_FRAME_LEN = 4`、`LOCK_KEY_FRAME_INDEX = 1` | 同上 |
| `K_L` 生成/读取 | `lock_key_generate()` / `get_lock_key()` | `common/encrypt/encrypt.c` |
| **密钥帧组包** | `lock_key_build_frame()`：4 字节随机，下标 1 写入 `K_L` | 同上 |
| 加解密 | `data_xor_crypt(rand, key, data, len)`（自反，收发共用），内部 `key = rand ^ key` | 同上 |
| 上电广播 | `lock_fsm_power_on` 的 ENTRY 开头：生成 `K_L` → 发 `0x70` | `fsm/state/fsm_state_power_on.c` |
| `0x71` 处理 | 收到即回 **`0xF1` + 4 字节密钥帧** | `handler/uart_protocol_request_key.c` |
| cs2 失配 | 主动重发 `0x70` + 4 字节密钥帧（等 `0xF0`） | `protocol/uart_protocol.c` |
| ACK 处理 | `IS_UART_ACK_CMD` 统一清重传（`0xF0`/`0xF1` 自动覆盖） | 同上 |
| `0x70` 重发 | 依托 ACK 重传（300ms × 2）；仍失败则由对方 `0x71` 驱动重同步 | — |

**门锁侧不需要周期重发 `0x70`** —— 失败时由 WiFi 的 500ms `0x71` 请求兜底。

## 8. 验证方法

| 观察点 | 正常表现 |
|---|---|
| 门锁上电 | 发 1 次 `0x70`，payload 4 字节，300ms 内收到 `0xF0`，无 `UART retry/timeout` |
| WiFi 侧日志 | `lock key updated: 0xXX`，且 `0xXX` 等于门锁日志中 `0x70` payload 的**第 2 个字节** |
| 门锁日志 | 不出现持续的 `checksum2 fail` |
| 门锁重启后 | WiFi 发一次 `0x71`，门锁回 `0xF1`（4 字节），随后业务恢复 |
| WiFi 重启后 | 同上（WiFi 无密钥 → 主动 `0x71`） |
| 全链路 | 两侧均无持续 retry / cs2 告警 |

**联调步骤**：
1. 双方先只开"收方向"（能解对方加密帧），验证 `0x70 → 0xF0` 握手
2. 核对两侧的 `K_L` 是否一致（取密钥帧第 2 字节）
3. 再开发方向加密，验证 5.2 / 5.3 两个自愈场景（重启门锁 / 重启 WiFi 各一次）
4. 验证 5.4（门锁主动补发）

## 9. 待确认项

| 项 | 状态 |
|---|---|
| `K_F = 0xBA` | ⚠️ **双方固件写死后锁定**，不一致会导致握手失败 |
| **密钥帧取下标 1** | ⚠️ **双方必须一致**（固定位置，不做"第 N 个非 00"扫描）；非法值 `0x00/0xFF` 视为无效 |
| `R` 的生成方式 | 门锁侧用 `R = (sn * 0x1F + 0x37) & 0xFF`（随帧变化即可，真正保密的是 `K_L`）；WiFi 侧可任选，只要写进帧头 |
| `0xF1` 丢失的兜底 | 靠 WiFi 侧 500ms 限频的 `0x71` 重试，不需要额外机制 |
| 门锁侧随机源 | 本芯片**无硬件随机数**：`K_L` 由**上电 tick** 派生，因此**同一毫秒上电可能得到相同密钥**（可接受：最坏只是 WiFi 不必重新同步）。非密码学强度，仅防串口抓包直读明文；若要求密钥不可预测，需换 **AES/SM4 + 真随机源**（`attr` 的 bit4~5 还有 `2`/`3` 两个值可用，帧格式无需改） |
