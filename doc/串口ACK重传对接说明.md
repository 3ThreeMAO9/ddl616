# 门锁 ↔ WiFi 模块 串口 ACK / 重传 对接说明

版本：v1.0（2026-10-16）
背景：**门锁侧已启用"发送等 ACK + 超时重传"机制**，请 WiFi 侧同步实现应答与重传，否则会出现门锁反复重发、业务超时。

---

## 1. 链路与帧格式

- UART：**230400, 8, N, 1**
- 地址：门锁（前板）= `ADDR_FRONT(1)`，WiFi 模块（后板）= `ADDR_WIFI(3)`

帧头 12 字节（`lock_packet_t`，pack(1)）：

| 偏移 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0 | mark | 1 | 固定 `0xA5` |
| 1 | attr | 1 | bit0~3 = 地址，bit4~5 = 加密类型（0=不加密） |
| 2 | checksum1 | 2 | 头部校验，见下 |
| 4 | sn | 2 | 序列号（小端） |
| 6 | cmd | 1 | 命令字 |
| 7 | random | 1 | 加密随机数（不加密填 0） |
| 8 | checksum2 | 2 | payload 校验 |
| 10 | length | 2 | payload 字节数 |
| 12 | payload | N | 数据 |

- `checksum1 = SUM(attr) + SUM(sn ~ payload)`
- `checksum2 = SUM(payload)`

## 2. ACK 定义（请双方统一）

1. **ACK 命令字 = 请求命令字 | 0x80**（把最高位置 1）
   - 例：门锁发 `0x62`（入网）→ WiFi 回 `0xE2`
2. **ACK 包不再需要被应答**（收到最高位 = 1 的包，一律不回应答，避免死循环）
3. ACK 的 payload 一般为**空**（属性类见 §5）
4. **任一命令字在两个方向都能出现**（例：`0x16` 既可能是 WiFi 下发的请求，也可能是门锁主动上报）。
   方向由帧头的 **`attr` 低 4 位（addr）** 区分：门锁 = `1`（前板），WiFi 模块 = `3`（后板）

## 3. 门锁侧已实现的行为（本次启用）

| 项 | 值 |
|---|---|
| 重传间隔 | **300 ms** |
| 最大重传次数 | **2 次**（首发 + 2 次重传 = 最多 3 次） |
| 等待 ACK 期间 | **不发送新包**（发送队列串行；前一包收到 ACK 或超时后，才发下一包） |
| 重传内容 | **原包原样重发**（sn、payload 都不变） |
| 收到 ACK | **只按"原命令字"匹配**（不判断 sn，见 §3.1） |
| 超时（重传 2 次无 ACK） | 放弃该包，允许发下一包；业务层自行处理失败 |
| 对收到的每一包请求 | **都会回 ACK（`cmd\|0x80`）** |

### 3.1 当前实现的三个简化（WiFi 侧可照做）

1. **不加密**
   `ENCRYPT_EN = false`；发送时 `attr` 的加密位恒为 0、`random` 恒为 0，payload 明文传输（加密模块整体未参与编译）。
2. **不判断 sn**
   门锁（前板）与 WiFi 模块（后板）**各自维护自己发送帧的 sn**（各自从 0 自增），**双方都不校验 sn**：
   - 收到 ACK 时**只比较命令字**，不看 sn；
   - 发送是**串行的**（同一时刻只有一个待确认包），不存在张冠李戴；
   - 重传沿用原 sn、内容原样重发，但对方不依赖它。
3. **收到对应 cmd 即停止重传**
   只要收到「原命令字 | 0x80」，无论 sn 是否一致、payload 是否为空，都清重传并允许发下一包。

**唯一的完整性校验**：帧头的 `checksum1` 与 payload 的 `checksum2`，校验不过直接丢弃。

> 注意：**除 ACK 外，门锁发出的每一包都要求对端回 ACK**。当前包括：按键 `0x60`、门铃 `0x61`、入网 `0x62`、蓝牙 MAC `0x63`、蓝牙版本 `0x64`、事件上报 `0x45~0x47`，以及后续可能用到的属性主动上报（`PROP_CMD_*`）。
> 门锁发出的**应答**（最高位 = 1，如属性应答 `0x96`）本身就是 ACK，**不需要对端再回应答**。

## 4. 请 WiFi 侧实现

### 4.1 收方向：对门锁的每一包回 ACK

| 门锁发来 | WiFi 应回 | 备注 |
|---|---|---|
| `0x60` 按键事件 | `0xE0` | |
| `0x61` 门铃事件 | `0xE1` | |
| `0x62` 入网请求 | `0xE2` | |
| `0x63` 蓝牙 MAC 请求 | `0xE3` | |
| `0x64` 蓝牙版本请求 | `0xE4` | |
| `0x45 / 0x46 / 0x47` 事件上报 | `0xC5 / 0xC6 / 0xC7` | **需新增** |
| 收到 ACK（最高位 = 1） | **不应答** | 防止死循环 |

> 属性命令（`0x10~0x37`）不列在此表：它们是 WiFi 下发的读/写请求，门锁回的 `cmd|0x80` 属于"应答"，**WiFi 不需要再回应答** —— 详见 §5。
> 但**门锁主动上报属性时，WiFi 必须回 `cmd|0x80`**（见 §5.2 第 3 条）。

### 4.2 发方向：等 ACK + 重传（与门锁对齐）

- 参数**与门锁一致**：**300 ms 超时 / 最多重传 2 次**
- **各自维护自己发送帧的 sn**（从 0 自增），**不校验对端的 sn**
- 重传时**原样重发**（sn、payload 都不变）
- 等待 ACK 期间建议串行（不发新包），或自行做队列管理
- 超时后按业务失败处理（例：给 APP 返回失败）

## 5. 属性类命令（`0x10 ~ 0x37`）

> 方向与 ACK 规则同 §2，本节只说明这几个命令的 **payload 格式**。

### 5.1 报文格式

| 角色 | 命令字 | payload |
|---|---|---|
| 发起方 | **`PROP_CMD_*`**（如 `0x16`） | 读/写请求：`[opt(1字节), data...]`（`opt`：0=读取，1=设置；读取时只有 `opt`）<br>属性上报：属性值 |
| 接收方 | **`PROP_CMD_* \| 0x80`**（如 `0x96`） | 读请求的应答：属性值（即"ACK + 值"）；其它：空 |

### 5.2 要求 WiFi 侧改动

1. **`async_send_property`**：`msg.timeout_cmd = cmd` → **`cmd | 0x80`**（等待门锁的 ACK）
2. **`lock_packet_handler()` 的"匹配成功"分支**要处理属性：读请求的应答是"ACK + 值"，需按 `cmd` 范围（`0x10 ~ 0x37`）把 payload 交给 `ob_lock_prop_report_dispatch()` 上报云端
3. **对门锁主动上报的属性包（`PROP_CMD_*`）回 ACK**：`PROP_CMD_* | 0x80`，空 payload

### 5.3 门锁侧实现

- **收到读/写请求** → 回 `PROP_CMD_* | 0x80` + 属性值
- **主动上报**：门锁侧各属性变化目前都有对应事件通道（`0x40 ~ 0x59`），暂未使用属性上报；后续需要时按同样规则发 `PROP_CMD_*` + 值即可

```
WiFi → 门锁 : 0x16 + [opt]        属性读请求
门锁 → WiFi : 0x96 + 属性值        应答（ACK + 值）
```

> 应答包最高位=1，按 §2 不需要被应答，因此**不参与重传**；门锁发完即可处理下一包。

## 6. 时序示例

### 6.1 正常（一次成功）

```
门锁 → WiFi : 0x62 入网请求        (sn=01)
WiFi → 门锁 : 0xE2  ACK            (sn=01)   ← 300ms 内
门锁 → WiFi : 0x60 按键事件        (sn=02)   ← 收到 ACK 后立即可发下一包
WiFi → 门锁 : 0xE0  ACK            (sn=02)
```

### 6.2 丢包重传

```
门锁 → WiFi : 0x62 入网请求        (sn=01)
                 ← 300ms 无 ACK
门锁 → WiFi : 0x62 入网请求        (sn=01)   ← 重传第 1 次（内容完全相同）
WiFi → 门锁 : 0xE2  ACK            (sn=01)
```

### 6.3 超时放弃

```
门锁 → WiFi : 0x62 入网请求        (sn=01)
门锁 → WiFi : 0x62 入网请求        (sn=01)   ← 重传 1
门锁 → WiFi : 0x62 入网请求        (sn=01)   ← 重传 2
门锁 → WiFi : 0x63 蓝牙MAC请求     (sn=02)   ← 放弃 0x62，发下一包
```

## 7. 验证方法

**门锁侧日志（正常时不应出现）：**

```
(UART) UART retry 1 times (max=2) cmd = 0x62
(UART) UART tx timeout (retry 2 times)
```

**正常表现：** 每发一包请求，**300 ms 内**必有一条对应的 `cmd | 0x80` 回来。

**建议联调步骤：**

1. 只开"回 ACK"（WiFi 侧），先跑通门锁的按键/门铃/入网，观察门锁日志无 retry / timeout
2. 再开 WiFi 侧"发方向重传"，制造一次丢包验证重发
3. 最后联调属性读写（§5）
